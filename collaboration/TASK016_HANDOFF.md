## 1. Product objective
**General-purpose, evidence-driven Agent Readiness** — not a stock-visibility tester. Given a website URL and optional owner goals, the product should: inspect the site; generate representative tasks (hybrid: owner-defined + autonomous); freeze tasks and independently checkable success criteria; run live baseline agent trials; collect outcomes and traces; **autonomously investigate friction**; recommend evidence-backed, testable interventions; apply *approved* fixes in a controlled environment; rerun independent trials; and report **improvement, regression or inconclusive**. The loop it already demonstrates on a synthetic store: *baseline → identify friction → recommend a change → modify the site → rescan → measure whether it helped.* Non-negotiables from the owner: never hand-pick the diagnosis; keep **observation / hypothesis / supported finding / proposed fix / measured effect** separate; attribute failures carefully (website vs agent vs task vs environment vs provider/budget); support **"no supported issue"** outcomes; preserve negative and inconclusive results.

## 9. Open design questions to resolve before implementing
1. **Task generation:** how are tasks derived from an unknown site (probe → candidate journeys → LLM proposal) and *frozen* with deterministic, independently checkable success criteria (what oracle exists for an arbitrary site? answer-extraction from DOM/HTTP vs. state checks vs. human-supplied)? 2. **Leakage:** how to guarantee the agent under test cannot see criteria/ground truth, and the investigator cannot see held-out checks. 3. **Investigator design:** what an LLM investigator may read (traces, DOM snapshots, HAR), which tools it gets, how page content is treated as untrusted (prompt injection), and how its hypotheses are verified deterministically. 4. **Data model:** observation / hypothesis / supported finding / proposed fix / measured effect — schema, ids, provenance and how it extends the current `remediation-audit-v1` report. 5. **Attribution taxonomy** across website / agent / task / environment / provider, and the "no supported issue" outcome. 6. **Interventions on a real site:** what does "apply approved fixes in a controlled environment" mean for an arbitrary URL (sandbox clone, proxy/patch layer, owner-supplied staging, managed targets only)? 7. **Experiment design for arbitrary tasks/fixes:** paired blocks, controls, sample sizes and budget per investigation under the A$ ceiling. 8. **Provider configuration** (Meta preferred, pluggable) and cost model for LLM generation/investigation. 9. **Probe coverage:** JS-rendered pages (Playwright probe?), more markup families/attributes, robots/consent/ownership rules for auditing third-party URLs. 10. **Replacing `scanner/diagnostics.py`** without breaking the Scanner tab. 11. **How to test discovery honestly** (planted issues the system is not told about; negative controls). 12. **Demo path** for the hackathon deadline vs depth.

## Phase A — free configuration audit (no network, no model call)
- Endpoint `https://api.meta.ai/v1` + `/chat/completions`, model `muse-spark-1.3`, `Authorization: Bearer <key>` and `Content-Type: application/json`, body `{model, messages, max_completion_tokens, response_format}`: all match `docs/META-INTEGRATION.md`.
- Credential: `.env` loads via `load_repo_env()` (explicit repo-root path, no override), mode 600; the value is 48 ASCII characters, unquoted, no whitespace or inline comment (shape checked, value never printed). Credential problems in the file are not indicated; whether the key is *valid* is unknown.
- **Where the cause was lost:** `MetaClient.complete` caught every failure, re-raised `RuntimeError("model request failed (<Type>)…") from None`, and recorded neither the HTTP status nor the provider's message; `l0.run` then stored only `type(exc).__name__`. The ledger shows no `settle` entry, which in this code is written only after a 200, so the failure was a non-200 status or a transport error.
- **Strongest lead (unverified):** the P1 schema is `Echo.model_json_schema()`, which has no `additionalProperties: false`, while the integration notes say Meta's strict subset requires an object root, all properties required **and `additionalProperties: false`**. The taskgen models use `extra="forbid"` (they emit it); the L0 probe models do not, so L0 P1 may have been rejected for a reason that does not apply to taskgen. This is a hypothesis; the HTTP status was not captured. No change was made to the probe's request.
- **Ledger:** an unsettled reservation is the designed behaviour (non-200 keeps the full upper bound counted). It lives only in `investigations/l0-probe/spend/ledger.jsonl` (L0's own US$0.10 ledger) and is not read by `budget.py` / the programme ledger (A$43.79 remaining is unaffected). It was not modified. Consequence: re-running L0 into the *same* `--out` directory would count that reservation, start at request index 2 (id `…:req02`) and leave 5 of the 6 permitted requests; a clean rerun should use a new `--out`. Either way each rerun needs your explicit approval.

## Phase B — code changes
- `investigate/llm/meta.py`: new `ProviderError(RuntimeError)` with `category` (`transport` | `http` | `parse`), `status`, short sanitized `summary`. Transport: timeout vs other httpx error (class name only). HTTP: status plus the provider's own `error.type/code/message` when the body is JSON (≤160 chars each, key/`Bearer`/`sk-…` redacted), otherwise the reason phrase; never the raw body, headers or request. Parse (200, wrong shape): class name only. Settlement, reservations, caps, retries and the gate are unchanged. Model-output validation stays a separate layer (`StructuredOutputError`).
- `investigate/l0.py`: for a `ProviderError` the result row also records `error_category`, `http_status`, `error_summary`. `error` keeps the exception class name; stopping rule, evaluation and caps unchanged.
- Tests (`tests/test_investigate_llm.py`, 12 new cases): HTTP 400/401/403/429/500 with a JSON error body that echoes the key; non-JSON and 5 kB bodies (no raw text); timeouts (read/connect), connection error, protocol error; three 200-parse shapes; model-output validation still separate; L0 report integration (one request, probe stops, no key/prompt/bearer in the report, one reservation).

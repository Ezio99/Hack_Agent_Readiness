Branch `task016-m3-taskgen` (stacked on `task016-l0-probe`, PR #36). **No paid call, no model call, no external crawl, no frozen-file or ledger edit.** All model behaviour in tests is scripted/recorded; all agent behaviour is a scripted mock labelled as such.

## What was built (`src/agent_readiness/investigate/`)
| module | purpose |
|---|---|
| `taskgen/criteria.py` | Closed criterion set with a deterministic extractor and independent grader each: `page_fact` (fact retrieval), `reach_page` (navigation), `item_set` and `extremum` (cross-page filtering / comparison). A criterion names *where* the answer lives; **the expected answer is always re-derived from the snapshot** (never supplied by a model or owner). Unit-aware numeric comparison, exact normalised matching (a short sentence containing the phrase passes; a list of alternatives does not), set grading with precision/recall |
| `taskgen/gate.py` | Acceptance gate for every candidate (model, owner or rule): compiles; stable under re-extraction; evidence reachable by links from the start page within 4 hops and ≥ 1 navigation; answer not on the start page, not in the question, not yes/no; sets select some-but-not-all; ambiguity checks (question must name the entity / thresholds / field); duplicate detection (same criterion, or near-identical wording **with the same answer**); `assert_blind` on the question. Rejections keep a reason that contains no expected answer |
| `taskgen/propose.py` | Model-agnostic (`LLMClient`) proposer: factual site summary + rules → `TaskProposals` (flat strict-friendly criterion draft, all fields required, nulls for unused). One replacement round feeds back **rejection reasons only** |
| `taskgen/candidates.py`, `goals.py` | Deterministic rule candidates (offline baseline / top-up; no domain vocabulary) and owner goals (focus text + explicit tasks, same gate) |
| `taskgen/freeze.py` | Immutable public `tasks-manifest` (question, start page, kind, partition, limits, answer schema, snapshot hash, criteria hash; **no truth, no locators**) + private mode-0600 `private/criteria.json`; hash-linked load that detects any edit after freezing or a different snapshot; deterministic kind-spread **investigation/holdout partition**; `investigator_view` (investigation partition only, public fields only); builds independent `suite.core.TaskInstance`s (dynamic answer model, grader, evidence requirements) |
| `taskgen/stage.py` | `taskgen` and `freeze` pipeline stages; unusable model output is recorded and rules top up; fewer than 4 acceptable tasks fails loudly after writing the rejection report |
| `trials/runner.py`, `trials/stage.py` | **Thin M4**: one generated task on the read-only mirror through the real Browser Use agent (`mock` scripted agent or `live`), bounded, independently graded, journey/mirror-log/metrics recorded; `baseline_trials` stage: every frozen task × K repeats, one attempt each, durable per-trial artifacts, resumable, live runs behind the reserve-before-send gate, void/halt ends the stage |
| `flow.py`, CLI `investigate run` | The runnable chain inspect → taskgen → freeze → baseline_trials. `--mode mock`: rule tasks + scripted agent, no key. `--mode live`: Meta proposes tasks (stage `taskgen`) and Meta is the agent (stage `baseline_trials`); **each spending stage waits for your approval of its exact manifest hash**; the model client is constructed lazily so no key is read and nothing touches the network until after approval and the shared `ledger.preflight` |
Also: `InvestigationRun.write_private/private` (write-once 0600), item-name extraction in the page model (heading / first table cell fallback — needed because `site-2`'s only item links are icon-only, itself a planted-friction signal).

## Architectural notes / deviations
1. `reach_page` tasks are model/owner-only (a rule cannot phrase a page description without leaking its title). Rule candidates cover fact / set / comparison.
2. The taskgen prompt does contain the site's own field values (the summary lists sample values per field); that is public site content, not the private criteria. The private truth is derived *after* proposals and never reaches a prompt (the feedback round carries reasons only; tested).
3. Tasks start at the entry page `/` by default, which is what makes "not answerable from the first observation" hold even on a clean site whose listing cards already show the decisive fields.
4. The thin M4 runner is a copy-adapt of the frozen `execute_scan` (as the plan said); `baseline_trials` is the only M4 piece built so far — attribution, schedules, repeats beyond K, void classification beyond the status list and the full stage set remain M4/M5.
5. Mock agents are scripted navigators; they validate plumbing, grading and evidence logic, not model behaviour.

## Remaining risks
- **Unverified on the hosted model:** strict-schema output with nested `$defs` (TaskProposals), proposal quality and yield after the gate, and agent behaviour on generated tasks. L0 (P3/P5 use nested schemas) answers the first; the live slice answers the rest.
- Question wording from rules is stilted; model wording may be ambiguous in ways the token-based ambiguity checks cannot see — the gate catches clear failures only, and genuinely ambiguous tasks will show up as unexplained failures (attribution class `task_invalid`, M4).
- Heuristic item/fact extraction limits which real sites yield `item_set`/`extremum` tasks.

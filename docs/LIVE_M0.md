# Live evaluation, milestone M0 (mock execution)

What it is: a vertical slice of the product experience on registered demo sites. A user picks a website and states a goal in the **Investigation** page; the backend starts a bounded **real** job that runs the existing resumable investigation pipeline; the page polls durable state and shows stages, progress, trace events and recorded cost; the finished run opens in the same report view and can be reopened later with no execution.

## Run it locally
```
export SCANNER_DATA_DIR=scanner-data SCANNER_CORS_ORIGINS=http://127.0.0.1:4173
readiness scanner invite --label me --scans 5            # prints a one-time code
readiness scanner serve --port 8100                      # API (loopback)
cd dashboard && VITE_SCANNER_API_URL=http://127.0.0.1:8100 npm run build && npx vite preview --port 4173
```
Open `http://127.0.0.1:4173/#/investigation`, enter the code, choose a website, write a goal, **Start mock evaluation**. Live runs are stored under `$SCANNER_DATA_DIR/live/<job-id>/` (Git-ignored; override with `LIVE_ROOT`), never under `investigations/`.

## Architecture and seams (reuse, not rewrite)
| piece | where | note |
|---|---|---|
| target registry | `live/targets.py` | registered ids only (Ironbark, one zoo site); **no URL field exists anywhere** in the API |
| job manager | `live/jobs.py` | validation, one running job, 900 s timeout, cancel, restart recovery, status derived from the run directory |
| worker | `live/worker.py` | one subprocess per job (`python -m agent_readiness.live.worker`), environment scrubbed of anything credential-like; runs `investigate.flow.build(...)` unchanged, via the new `snapshot` option |
| routes | `live/api.py`, mounted in `scanner/service/api.py` | same sessions, rate limit, body limit, kill switch (`/api/admin/kill` also stops live jobs) |
| UI | `dashboard/src/pages/LivePanel.tsx`, `lib/liveApi.ts` | mounted on the Investigation page; results open in the existing report view |
| replay | `GET /api/live/jobs/{id}/export` | `investigation-dashboard-v1`, sanitized by the existing exporter; executes nothing |

## What is real, what is stubbed
Real: the background job and its lifecycle; capture of the site; rule-based task generation; the unchanged trial runner driving **real Chromium** against the captured site; trace analysis; the deterministic claim verifier; recommendation and report stages; the durable run directory, spend ledger and export.
Stubbed (every screen and the export say MOCK): the **language model** (no call is made) — tasks are generated by rules and **the goal is recorded but does not steer them**; the browser agent is the scripted mock agent; the investigator is a scripted test double (`live/mock_investigator.py`) that chooses *what to look at*, while the claim it reports is checked by the real deterministic verifier; the single proposal is an unvalidated hypothesis and is labelled so.

## M1 (not started) replaces, without UI changes
`worker.execute` mode `live`: LLM-driven discovery and task generation steered by the goal, the Meta model as the browsing agent and as investigator (the flow already supports `mode=live`), with a per-job hard cap (US$2 planned), explicit start confirmation, server-side key, and per-stage spend through the existing ledger. The job contract (`mode`, `spend.hard_cap_usd`, stages, events, export) already carries these fields.
